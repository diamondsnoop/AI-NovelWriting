# 版本目标规划

这份文档的目标不是罗列所有想做的功能，而是给开发设定清晰的版本边界，避免后续进入“想到什么做什么”的盲目迭代。

当前规划以已经完成的真实进度为基础：

- 主链路已真实跑通：`init -> plan -> write -> review -> summary -> query -> resume`
- 双版本大纲已稳定
- 字数压力测试已完成：`2000`、`3000` 字可跑
- `foreshadowing` 数据链已接入
- 最小 `retrieval` 检索链已接入
- 当前主要问题已经从工程链路，转向内容质量和策略调优

---

## 一、当前所处阶段

当前系统已经不在“骨架搭建期”，而是在：

**版本化完善期的第一阶段**

通俗说：

- 前一阶段解决的是“系统能不能站起来”
- 现在要解决的是“系统能不能稳定地连续写，并且不明显写崩”

所以后续版本目标应围绕这两个问题展开：

1. 当前版本怎样从“能跑”变成“可连续使用”
2. 后续版本怎样从“可用”变成“更像真正的长篇创作系统”

---

## 二、版本划分原则

后续版本建议按 4 个版本推进，每个版本只解决一类核心问题。

### 原则 1：先稳质量，再扩能力

如果当前审查、角色、人设、上下文承接还不稳，就不应该优先做 Dashboard 这类展示层。

### 原则 2：先补闭环，再补外围

优先补那些能进入主链路并改变写作结果的模块，而不是先做只读功能。

### 原则 3：每个版本都要有可验证目标

每个版本都必须能回答一句话：

**“这个版本上线后，系统比上个版本更能解决什么问题？”**

---

## 三、版本目标

## V0.2.x 已完成基线

对应当前远端状态：

- `v0.1.0-baseline`
- `v0.2.0-foreshadowing-retrieval`

这个阶段已经完成的目标：

- 建立可运行的工程骨架
- 打通真实 API 主链路
- 验证双版本大纲方案
- 验证 `2000` / `3000` 字写作长度可用
- 建立 `summary / entities / foreshadowing / retrieval` 的最小数据闭环

这一阶段已经解决的问题：

- `write` 因大纲过重导致的超时
- 第三方 API 调用模式不匹配
- 实体抽取文本格式不稳定

这一阶段仍遗留的问题：

- `character checker` 在数据薄时可能过严
- 人物画像存在名字漂移和单章定性偏薄问题
- `high_point / reader_pull` 仍未接入
- `foreshadowing` 只是数据链，尚未进入审查闭环

---

## V0.3.0 目标：内容质量稳定版

### 核心目标

让当前主链路从“可以跑通”，提升到“连续写几章后仍基本稳定”。

### 本版本重点

1. 调整 `character` 质量链
- 检查 `character_profile_summary` 的实际质量
- 判断主要问题是：
  - 单章数据太薄
  - 名字漂移
  - prompt 过于宽泛
- 再决定：
  - 改摘要 prompt
  - 还是改摘要累积策略
  - 最后才考虑 `gatekeeper` 阈值

2. 稳定 `structured_summary`
- 当前第 3 章曾出现 `key_events=[]`、`main_plot_advanced=false`
- 说明结构化摘要仍有稳定性问题
- 本版本应让结构化摘要输出更可靠，避免影响 `pacing` 和后续数据链

3. 把 `foreshadowing` 接入真实查询与初步消费
- 不只是写后落盘
- 还要确认：
  - 查询可读
  - 数据格式稳定
  - 后续审查可以读取

### 本版本验收标准

- 连续写 `5` 章时，`character checker` 触发拦截不超过 `1` 次
- 且该次拦截经人工复核后，确认为真实人物偏离问题
- `structured_summary` 的关键字段稳定输出
- `foreshadowing` 可稳定生成并可查询
- 主链路不因内容调优而回退

### 一句话定义

**V0.3.0 解决“系统会不会过早把自己写死”的问题。**

---

## V0.4.0 目标：长篇记忆增强版

### 核心目标

让系统开始具备更像长篇连载工具的上下文管理能力。

### 本版本重点

1. 强化 `retrieval`
- 当前只有最小 BM25 风格检索
- 本版本应补：
  - 查询路由
  - 更稳定的片段切分
  - 检索结果去重
  - 检索结果压缩

2. 让 `foreshadowing` 进入审查层
- 增加最小伏笔检查
- 检查：
  - 新伏笔是否足够清晰
  - 旧伏笔是否被矛盾覆盖
  - 伏笔是否长期悬空

3. 开始补 `plan` 的上层能力
- 章节大纲之外
- 增加：
  - 卷级规划
  - 节拍表
  - 时间线基础结构

4. 为 `high_point` 和 `reader_pull` 准备数据字段
- 在结构化摘要中补充：
  - 强情节/爽点节点标记
  - 章节结尾拉力标记
- 这一步只做数据准备，不在本版本接入 checker 逻辑

### 本版本验收标准

- 写作组包不只依赖最近一章摘要
- 系统能召回更相关的历史片段
- 伏笔不再只是“存起来”，而是能参与检查
- `plan` 不再只是逐章推进

### 一句话定义

**V0.4.0 解决“写到中长篇后会不会失忆”的问题。**

---

## V0.5.0 目标：六维审查成型版

### 核心目标

让审查系统接近开发基线文档里规划的完整形态。

### 本版本重点

1. 接入 `high_point`
- 使用 `V0.4.0` 已准备好的强情节/爽点标注字段

2. 接入 `reader_pull`
- 使用 `V0.4.0` 已准备好的章节结尾拉力标注字段
- 重点检查：
  - 是否留下追读动力
  - 是否存在“软着陆”导致阅读动力下降

3. 优化 `gatekeeper`
- 不再只按简单分数拦截
- 而是区分：
  - 严重问题必须拦截
  - 中等问题只告警
  - 轻微问题进入报告

### 本版本验收标准

- 六维审查里大多数维度已真实接入
- 审查结果不再是“有无”，而是更细的分级
- 用户能明显感受到系统对“章节质量”的判断更成熟

### 一句话定义

**V0.5.0 解决“系统会不会只会写、不知道什么叫好章节”的问题。**

---

## V0.6.0 目标：用户协作与展示版

### 核心目标

补齐“用户参与决策”和“可视化管理”这两层。

### 本版本重点

1. 扩展 `decision` 触发场景
- 从覆盖写入扩展到语义触发
- 典型场景：
  - 审查发现严重问题时询问用户
  - 设定冲突时让用户裁决
  - 方向分叉时让用户选路线

2. 补 `presentation`
- Dashboard
- 健康报告
- 项目状态概览

3. 视情况补 `learn`
- 这一项排最后
- 只有在系统已经积累足够多的写作数据后才有意义

### 本版本验收标准

- 用户不再只是“触发命令的人”，而是能在关键节点主动决策
- 项目数据不再只藏在 JSON 和目录里，而是能更容易被看懂

### 一句话定义

**V0.6.0 解决“系统是否真的像一个长期协作工具，而不是一堆脚本”的问题。**

---

## 四、当前版本之后的直接开发顺序

基于现状，建议严格按下面顺序继续：

1. `character_profile_summary` 质量分析
2. 决定是改 prompt 还是改累积策略
3. 再看 `gatekeeper` 阈值
4. 稳定 `structured_summary`
5. 验证 `foreshadowing` 的真实质量
6. 再进入 `retrieval` 的增强而不是重做

这一步顺序不能倒。

---

## 五、结论

当前最合理的版本目标安排是：

- `V0.3.0`：内容质量稳定
- `V0.4.0`：长篇记忆增强
- `V0.5.0`：六维审查成型
- `V0.6.0`：用户协作与展示

一句话概括：

**先解决“写得稳”，再解决“记得住”，再解决“审得准”，最后解决“用得顺”。**

## 六、V0.6.0 关版后待办（不阻塞关版）

1. `foreshadowing_checker` 误报率评估
- 待办状态：`pending`
- 执行时机：在同一验收项目追加到 `8-10` 章后执行

- 调整边界：仅允许调规则阈值、关键词提取与告警文案，不改模块调用方向与状态分层
