# Codex 长篇小说系统模型与运行时约束说明

## 0. 文档目的

这份文档只解决一个问题：

在这个项目里，“Codex”到底指什么，系统运行时到底依赖什么。

如果这件事不先说清楚，后面的 `foundation.llm_client`、`creation`、`review` 和整体代码骨架都会变成空壳。

## 1. 术语定义

### 1.1 本项目中的 “Codex” 是什么

在本项目里，“Codex”主要表示：

- 我们当前参考的开发协作形态
- 我们想承接的产品方向
- 我们在 OpenAI 生态中的实现定位

它**不是**一个必须作为产品运行时宿主存在的硬依赖。

### 1.2 本项目中的 “运行时” 是什么

“运行时”指的是：

- 用户真正执行小说创作系统时，系统背后依赖的模型调用方式和流程执行环境

运行时真正必须存在的，不是 Codex 宿主，而是：

- 足够强的模型能力
- 稳定的 API 调用入口
- 我们自己的工作流系统

## 2. 运行时总原则

### 2.1 最终产品不绑定 Codex 宿主

本项目不是“必须运行在 Codex 里的系统”。

本项目应定义为：

**一个以强模型 API 为底座、借鉴 Codex/Claude Code 协作形态的长篇小说创作系统。**

也就是说：

- 可以参考 Codex 的开发方式
- 可以在 Codex 环境里开发
- 但最终产品能力不绑定 Codex 宿主本身

### 2.2 产品运行时绑定“模型能力”，不绑定“某个特定代理外壳”

产品运行时真正依赖的是：

- 模型推理能力
- API 可调用性
- 成本、稳定性、时延可控

而不是：

- 某个特定 IDE 插件
- 某个特定代码代理界面
- 某个特定 slash command 宿主

## 3. 第一阶段运行时选择

### 3.1 第一阶段采用“单主后端”

第一阶段应采用：

- 单一主模型后端

原因很简单：

- 先把系统主链路跑通
- 先把写作、审查、询问、恢复的闭环做稳
- 避免一开始就在多后端适配上分散精力

### 3.2 架构上保留多后端适配能力

虽然第一阶段只接一个主后端，但架构上必须允许以后扩展为：

- 多模型后端
- 不同任务使用不同模型
- provider 切换

也就是说：

- 当前实现可以单后端
- 但接口设计不能写死成“只认一个供应商”

### 3.3 当前阶段的正式口径

当前项目的正式口径应是：

- 运行时依赖强模型 API
- 不依赖 Codex 作为运行时宿主
- `foundation.llm_client` 必须面向可替换 provider 设计

## 4. `foundation.llm_client` 的职责边界

### 4.1 它负责什么

`foundation.llm_client` 负责：

- 提供统一模型调用入口
- 统一请求格式和响应格式
- 统一超时、重试和错误处理
- 统一记录调用日志、成本和时延
- 屏蔽不同 provider 的接口差异
- 为不同任务应用不同调用配置

### 4.2 它不负责什么

`foundation.llm_client` 不负责：

- 小说工作流编排
- 多角色协作逻辑
- 审查器并行调度
- 用户询问流程控制
- 项目状态回写

通俗比喻：

- `llm_client` 像总机和线路适配器
- 它负责把电话打通
- 但不负责决定“该打给谁、先打哪个、打完怎么处理”

## 5. 是否需要 `agent_runtime`

### 5.1 结论

需要。

### 5.2 原因

本系统里已经存在很多超出“单次模型调用”的行为：

- 章节写作的多阶段执行
- 审查模块的内部多检查器协作
- 决策信号的语义判断
- learn 过程中的经验提炼
- 同一任务中不同角色的上下文组织

这些行为如果直接塞进 `llm_client`，会让它从“通信层”变成“万能层”，后面一定会失控。

### 5.3 `agent_runtime` 的职责

`foundation.agent_runtime` 或等价层，负责：

- 组织角色级任务执行
- 管理单个业务模块内部的多步调用
- 管理上下文注入和结果收敛
- 协调一次业务动作里的多个模型调用

它不负责全局流程编排。

### 5.4 `agent_runtime` 和 `workflow` 的关系

这两者必须区分清楚：

- `workflow`
  - 负责全局流程级控制
  - 决定写作、审查、询问、恢复的顺序

- `agent_runtime`
  - 负责单个业务动作内部的角色执行
  - 例如一次写作、一轮审查、一轮经验提炼

通俗比喻：

- `workflow` 像导演
- `agent_runtime` 像某个部门内部的小组长
- `llm_client` 像电话和线路系统

这三层不能混。

## 6. 对各模块的直接影响

### 6.1 对 `creation`

影响是：

- `creation` 不应直接绑某个具体模型接口
- 它应通过 `agent_runtime` 组织写作动作
- 再由 `llm_client` 去完成具体模型调用

### 6.2 对 `review`

影响是：

- `review` 的内部并行检查器，不应各自直接绑定 provider
- 应通过统一运行时调度，再统一走 `llm_client`

### 6.3 对 `decision`

影响是：

- 决策信号里的语义判断，也应走统一模型入口
- 不能单独形成另一套隐形调用链

### 6.4 对后续代码骨架

影响是：

- 代码骨架中必须预留 `foundation.llm_client`
- 代码骨架中必须预留 `foundation.agent_runtime`
- 在这两个基础层定清前，不适合直接把 `creation` 和 `review` 写死到具体模型 SDK

## 7. 当前阶段的硬规则

1. 最终产品不依赖 Codex 作为运行时宿主。
2. 运行时依赖强模型 API，而不是特定代理外壳。
3. 第一阶段采用单主后端，但接口设计必须允许未来多后端。
4. 所有模型调用必须统一经过 `foundation.llm_client`。
5. 多角色和多步执行逻辑不属于 `llm_client`，应由 `foundation.agent_runtime` 承担。
6. `workflow` 仍然是唯一流程控制中心，`agent_runtime` 不能越级替代 `workflow`。

## 8. 一句话总结

这个项目最终依赖的不是 Codex 这个名字，而是“强模型 API + 我们自己的系统骨架”。

把这件事说清楚之后，后面的开发就不会被宿主形式绑死。
