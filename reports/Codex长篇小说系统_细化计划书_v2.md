# 基于 Codex 的长篇小说创作系统细化计划书 v2

## 0. 本次修订重点

这份 v2 文档不是推翻原计划书，而是把上一轮架构审查中确认的调整正式落地。

本次重点修正 5 点：

1. `context_engine` 不再视为纯创作模块，而是提升为工作流层的“上下文组包能力”
2. 增加 `foundation.llm_client`，作为全系统统一模型调用入口
3. 检索层收敛为统一 `search_engine`，不在早期拆成多个平行搜索引擎
4. `decision` 触发机制改为“模型语义信号 + 规则信号”的混合方式
5. checkpoints 和 snapshots 统一并入状态层管理，不单独拆出快照平级模块

---

## 1. 产品目标不变

我们要开发的仍然是一个：

**基于 Codex 的长篇小说创作系统**

它的目标仍然是：

- 帮用户长期管理一部小说
- 帮用户持续产出章节
- 帮用户控制设定一致、节奏稳定、人物不崩
- 在关键节点把决定权交还给用户

一句话定义：

> 让 AI 和用户协同完成长篇小说创作闭环，而不是只做一次性正文生成。

10. RAG 检索辅助

## 3. 修订后的总体架构

系统建议拆成 8 层：

1. 交互入口层
2. 工作流编排层
3. 决策交互层
4. 创作执行层
5. 审查控制层
6. 记忆与检索层
7. 展示与运维层
8. 统一模型调用底座

### 3.1 交互入口层

负责：
- 接收用户命令
- 识别当前项目
- 启动具体流程

### 3.2 工作流编排层

负责：
- 定义 init / plan / write / review / query / resume / learn / dashboard 的流程
- 管理步骤顺序、模式差异、状态记录
- 负责章节执行包的组装

这里是本次修正的重点之一：

原先容易被误放到创作层的“上下文准备”，更准确地说是：
- 一种工作流桥接能力
- 作用是把多个来源的信息打包成可执行任务包

它不应做正文生成判断。

### 3.3 决策交互层

负责：
- 判断什么时候要停下来问用户
- 管理问题类型、选项、风险说明
- 记录用户裁决

这里是本次修正的第二个重点：

“是否该问”不应被设计成纯规则穷举。

更合理的设计是：

- 规则信号：
  - 覆盖写入
  - 恢复策略选择
  - 缺关键文件
  - 高风险动作确认

- 模型信号：
  - 设定冲突
  - 信息不足
  - 剧情方向分叉
  - 审查发现重大创作风险

也就是说：
- 低层硬条件靠规则
- 高层创作判断靠模型

### 3.4 创作执行层

负责：
- 初始化项目骨架
- 规划内容生成
- 正文起草
- 风格适配
- 润色修订

这层只消费工作流层给出的执行包，不自己四处读取项目状态、检索和大纲。

### 3.5 审查控制层

负责：
- 一致性检查
- 连贯性检查
- OOC 检查
- 节奏检查
- 爽点检查
- 追读感检查
- 汇总报告

### 3.6 记忆与检索层

负责：
- 状态文件
- 索引数据库
- 章节摘要
- 向量库
- 检索接口

本次修正点：

- 不再把 snapshots 作为独立平级模块
- checkpoints、snapshots、review checkpoints 统一归入状态层管理

这样可以避免：
- 一部分状态切片存在 JSON
- 另一部分存在另一个平级模块

### 3.7 展示与运维层

负责：
- 健康报告
- Dashboard
- 索引重建
- 状态诊断
- 测试辅助

### 3.8 统一模型调用底座

这是本次新增的关键层。

负责：
- 提供统一模型调用入口
- 统一管理写作、审查、决策等不同任务的调用参数
- 统一做超时、重试、错误处理
- 统一记录日志、时延、成本与观测数据

没有这一层，创作和审查模块都会变成“各调各的”的空壳。

## 4. 修订后的关键实现思路

## 4.1 初始化如何实现

实现方式不变：
- 先收集信息
- 再生成目录、模板、状态

但调用路径要统一走 `llm_client`，避免后面出现不同初始化子任务各自调用模型的碎片化问题。

## 4.2 规划如何实现

实现方式不变：
- 读取总纲与设定
- 生成节拍表、时间线、章节规划

重点是：
- 规划模块属于创作执行层
- 但规划前的数据聚合仍由工作流层负责组织

## 4.3 写作如何实现

修订后的写作流程应是：

1. 工作流层读取项目状态与章节要求
2. 工作流层组装章节执行包
3. 检索层提供相关召回结果
4. 创作层生成草稿
5. 创作层做风格适配
6. 审查层输出结构化报告
7. 决策层在必要时发起询问
8. 创作层做修补与润色
9. 记忆层回写状态、摘要与索引

其中最重要的边界是：

- 组包属于 workflow
- 正文生成属于 creation
- 判断是否有重大问题属于 review
- 决定是否需要用户拍板属于 decision
- 事实回写属于 memory

## 4.4 审查如何实现

实现方式不变，但调用方式收紧：

- 各检查器不自己随意调模型
- 统一通过 `llm_client`

这样做的目的：
- 保证参数一致
- 保证日志一致
- 保证后续切换模型时不需要满项目改

## 4.5 状态与索引如何实现

实现方式：
- 轻量运行状态放 JSON
- 高频查询和大对象放 SQLite
- 检索向量独立存储

修正后的约束：

- checkpoints、snapshots、review checkpoints 统一按“状态时间切片”管理
- 不再拆出独立快照子系统

## 4.6 RAG 如何实现

这是本次调整最明确的一块。

原先容易把它拆成多个并行引擎：
- bm25_engine
- vector_engine
- hybrid_engine

修正后建议：

- 对外只有一个 `search_engine`
- 内部用策略模式支持：
  - BM25
  - 向量
  - 混合
  - 后续图谱混合

保留的模块：
- `query_router`
- `search_engine`
- `rerank`
- `context_recall`

这样可以把早期开发复杂度降下来。

## 4.7 询问机制如何实现

修正后的实现原则：

- 不能只写触发规则表
- 要允许模型判断“这里是不是该问用户”

建议机制：

1. 规则先兜底
2. 模型再补语义判断
3. 一旦产生 `decision signal`
4. 再进入问题构建、选项组织、结果记录

## 4.8 恢复如何实现

恢复逻辑不变，但工作流状态管理要明确：

- 状态记录必须是跨 flow 的共享服务
- 不能是每个 flow 各记一套

否则 `write_flow` 中途调用 `review_flow` 时，状态会很快乱掉。

## 5. Claude Code 特性的修订后迁移方案

### 5.1 Slash commands

迁移为：
- 我们自己的统一命令系统

### 5.2 Skills

迁移为：
- 工作流定义
- 资源加载规则

### 5.3 Agents

迁移为：
- Codex 兼容的角色分工
- 或内部任务分工

### 5.4 Task 调子代理

迁移为：
- 我们自己的工作流编排器
- 以及统一的模型调用底座

### 5.5 AskUserQuestion

迁移为：
- 正式决策交互层

并且：
- 由规则信号和模型信号共同触发

### 5.6 项目定位与当前项目指针

迁移为：
- 我们自己的项目定位机制
- 保留“当前激活项目”能力

### 5.7 插件市场分发

不保留原形式。

这不是功能损失，只是宿主分发方式的变化。

---

## 6. 当前阶段必须保留的底层约束

在真正进入实现前，建议先把这几条视为硬约束：

1. 任何模型调用都走统一 `llm_client`
2. 任何章节写作都必须先由 workflow 组装执行包
3. 检索层对外只有一个统一 `search_engine`
4. 决策触发必须允许模型语义判断参与
5. 状态时间切片统一收口到状态层
6. 工作流状态跟踪必须是跨 flow 的共享服务

---

## 7. 这次修订的结论

这轮调整没有改变产品方向，只是让骨架更可实现。

最重要的变化是三条：

1. 上下文准备从“创作内部步骤”提升为“工作流桥接能力”
2. 模型调用从“各模块隐式依赖”提升为“基础设施”
3. 检索从“理想拆分”收敛为“统一对外入口”

这三条如果不先定，后面写代码时会不断返工。
