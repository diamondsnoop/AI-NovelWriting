# 模块调用方向与状态作用域规范 v2

## 0. 文档目的

这份文档只做三件事：

1. 规定模块之间允许的调用方向。
2. 规定哪些调用方向是例外，哪些方向被禁止。
3. 规定状态分层、状态作用域和日志归属。

这不是功能说明书，而是实现阶段的“护栏文档”。
它的作用是防止系统从分层结构慢慢滑成一张互相乱调的网。

## 1. 核心原则

### 1.1 `workflow` 是唯一流程控制中心

只有 `workflow` 可以决定：

- 下一步执行哪个业务模块
- 当前流程是否暂停
- 是否进入用户询问
- 是否继续、回滚、恢复或终止

其他模块都不能直接改变流程走向。

### 1.2 业务模块可以有内部调度，但不能越级控制全局流程

例如：

- `review` 可以在内部并行调度多个 checker
- `creation` 可以在内部组织草稿、风格适配、润色等子步骤

但这些都属于模块内部实现，不代表它们拥有全局流程控制权。

### 1.3 所有高影响分叉都必须回到 `workflow`

不管信号来自：

- `creation`
- `review`
- `retrieval`
- `workflow` 自己的规则检查

最终都只能返回给 `workflow`，由 `workflow` 决定是否进入 `decision`。

## 2. 一级模块

系统当前定义的一级模块：

1. `foundation`
2. `interaction`
3. `workflow`
4. `decision`
5. `creation`
6. `review`
7. `memory`
8. `retrieval`
9. `presentation`

## 3. 允许的主调用方向

### 3.1 标准主链路

允许的主调用方向如下：

- `interaction -> workflow`
- `workflow -> creation`
- `workflow -> review`
- `workflow -> retrieval`
- `workflow -> decision`
- `workflow -> memory`
- `workflow -> presentation`

这条主链适用于：

- 初始化
- 规划
- 写作
- 审查
- 查询
- 恢复
- 学习
- 启动 Dashboard
- 生成状态报告

### 3.2 基础设施调用

允许所有业务模块调用 `foundation` 提供的基础能力。

例如：

- `workflow -> foundation`
- `creation -> foundation`
- `review -> foundation`
- `decision -> foundation`
- `memory -> foundation`
- `retrieval -> foundation`
- `presentation -> foundation`

这里的调用只限基础设施能力，例如：

- 项目定位
- 配置读取
- 安全读写
- 统一日志
- 统一模型调用

`foundation` 不反向驱动业务流程。

## 4. 允许的例外方向

### 4.1 `interaction -> presentation`

这是唯一需要显式写出的例外。

允许：

- `interaction -> presentation`

但只限纯展示入口，例如：

- 打开只读 Dashboard
- 打开展示页面
- 展示已经生成好的报告文件

不允许：

- 在这条链路里做业务判断
- 在这条链路里推进流程
- 在这条链路里更新项目状态

通俗比喻：

前台可以帮你打开监控屏幕，但不能让监控屏幕反过来指挥生产线。

## 5. 禁止的调用方向

### 5.1 与 `workflow` 相关的禁止项

禁止：

- `creation -> workflow`
- `review -> workflow`
- `decision -> workflow`
- `memory -> workflow`
- `retrieval -> workflow`
- `presentation -> workflow`

解释：

- 这些模块不能反向控制工作流
- 它们只能返回结果或标准化 signal

### 5.2 与 `decision` 相关的禁止项

禁止：

- `creation -> decision`
- `review -> decision`
- `retrieval -> decision`
- `memory -> decision`

解释：

- 这些模块不能直接去“问用户”
- 它们只能返回 `decision_required` 或其他标准化 signal 给 `workflow`
- 是否进入 `decision`，必须由 `workflow` 决定

### 5.3 与 `memory` 相关的禁止项

禁止：

- `interaction -> memory`
- `presentation -> memory` 的业务写入
- `review -> memory` 的最终状态回写
- `creation -> memory` 的流程状态推进

解释：

- `memory` 只接收 `workflow` 组织后的正式写入
- 防止多个模块绕过流程，直接改项目真相

### 5.4 与 `presentation` 相关的禁止项

禁止：

- `presentation -> creation`
- `presentation -> review`
- `presentation -> decision`
- `presentation -> memory` 的业务写入

解释：

- 展示层不能变成隐形业务入口

## 6. 模块允许返回的内容类型

除 `workflow` 外，其他模块对外只能返回两类内容：

### 6.1 业务结果

例如：

- 章节草稿
- 审查报告
- 检索结果
- 状态读取结果
- 可视化内容

### 6.2 标准化 signal

例如：

- `decision_required`
- `missing_required_input`
- `conflict_detected`
- `recovery_risk_high`
- `write_blocked`

signal 的作用：

- 提醒 `workflow` 当前出现了需要处理的情况

signal 的限制：

- signal 不是命令
- signal 不能自己改变流程

也就是说：

- `review` 可以返回 `decision_required`
- 但 `review` 不能自己调用 `decision`

## 7. 并行审查规则

### 7.1 调度权归属

并行审查由 `review` 模块内部负责。

标准结构是：

- `workflow -> review`
- `review` 内部并行调度多个 checker
- `review` 汇总为统一报告再返回 `workflow`

### 7.2 为什么不由 `workflow` 直接调 checker

如果让 `workflow` 直接调多个 checker，会出现三个问题：

1. `workflow` 过度了解 `review` 的内部结构。
2. checker 组合一变，`workflow` 接口就跟着变。
3. `review` 会退化成一个很薄的拼接层。

因此必须明确：

- `workflow` 不直接调单个 checker
- checker 只属于 `review` 的内部实现
- `review` 对外是黑盒模块

## 8. `decision signal` 的消费规则

### 8.1 信号来源

`decision signal` 可以来自：

- `creation`
- `review`
- `retrieval`
- `workflow` 自己的规则检查

### 8.2 唯一消费者

所有 `decision signal` 的唯一消费者都是：

- `workflow`

### 8.3 标准处理链路

处理顺序必须是：

1. 某业务模块返回业务结果或 signal
2. `workflow` 接收该结果
3. `workflow` 判断是否需要进入 `decision`
4. 如果需要，再执行 `workflow -> decision`
5. `decision` 负责组织问题、选项、风险说明，并拿回用户裁决
6. 裁决结果返回 `workflow`
7. `workflow` 决定后续走向

结论：

- `decision` 不直接打断流程
- `decision` 不直接推进流程
- `decision` 只负责裁决交互

## 9. 状态分层

系统状态必须分层，建议分成 4 层：

1. 项目级长期状态
2. 任务级短期状态
3. 可恢复状态切片
4. 运行观测日志

## 10. 状态作用域规则

### 10.1 项目级长期状态

作用域：

- `project_id`

存放内容：

- 当前写到哪里
- 主角状态
- 世界状态
- 伏笔状态
- 关系状态
- 章节元信息
- 项目记忆

归属模块：

- `memory`

特点：

- 这是整本书的长期真相

### 10.2 任务级短期状态

作用域：

- `project_id + task_id`

存放内容：

- 当前执行的是哪个命令
- 当前执行到哪一步
- 哪些步骤已完成
- 哪些步骤失败
- 当前任务产物引用

归属模块：

- `workflow.state_tracker`

特点：

- 这是单次流程执行的短期状态
- 不等于项目级长期状态

明确规则：

`state_tracker` 的主作用域是任务，不是项目本身。
但任务必须挂在项目下，所以实际粒度是 `project_id + task_id`。

### 10.3 可恢复状态切片

作用域：

- `project_id`
- 必要时关联 `task_id`

存放内容：

- workflow checkpoints
- resume snapshots
- review checkpoints
- chapter execution snapshots

归属模块：

- `memory.state_store`

特点：

- 这些数据是结构化的
- 会被恢复流程和诊断流程再次消费

### 10.4 运行观测日志

作用域：

- 可按 project / task / process 多维记录

存放内容：

- 调用链日志
- 错误日志
- 性能日志
- 调试轨迹

归属模块：

- `foundation.logging`

特点：

- 只用于观测和排障
- 不作为业务恢复的真相来源

必须强调：

运行 trace 不属于状态层，它属于日志层。

## 11. 状态层与日志层的边界

属于 `memory.state_store` 的：

- checkpoint
- snapshot
- review checkpoint
- 可恢复执行切片

属于 `foundation.logging` 的：

- workflow trace
- 调用明细
- 错误堆栈
- 性能观测
- 调试输出

通俗比喻：

- `state_store` 像存档点
- `logging` 像监控录像

存档点用于恢复游戏进度。
监控录像用于事后排查发生了什么。
这两类东西不能混。

## 12. 最终硬规则

把前面的内容压缩成最关键的 10 条：

1. `workflow` 是唯一流程控制中心。
2. 业务模块只能返回结果或 signal，不能直接改流程走向。
3. 所有 `decision signal` 只能由 `workflow` 消费。
4. `creation`、`review`、`retrieval` 都不能直接调用 `decision`。
5. `review` 可以内部并行调度 checker，但对外必须保持黑盒接口。
6. `interaction -> presentation` 只允许纯展示入口，不允许业务判断。
7. `state_tracker` 的作用域是 `project_id + task_id`。
8. 可恢复切片归状态层，运行 trace 归日志层。
9. `memory` 只接受 `workflow` 组织后的正式写入。
10. `presentation` 不能成为隐形业务入口。

## 13. 一句话总结

这套规范真正要防的不是“功能不够”，而是“模块之间越写越乱”。
只要调用方向和状态作用域先封口，后面的实现再复杂，也不容易长成一张网。
