# V0.4.0 开发与验收清单（执行版）

## 0. 文档目的

这份文档用于固定当前 `V0.4.0` 的执行状态，明确三件事：

1. 这一版已经做完了什么。
2. 这一版还差什么才能关版。
3. 在 API 暂时不可用时，哪些部分可以先完成并验收。

---

## 1. 当前背景

- 当前阶段：`V0.4.0`（长篇记忆增强版）
- 本轮开发策略：先做可离线验证的结构和流程，API 恢复后补质量验证
- 当前限制：真实 API 暂时不可用

这意味着：

- 可以先完成数据结构、调用链、Mock 回归
- 暂缓“提示词质量”与“模型语义质量”的最终判断

---

## 2. V0.4.0 范围（本执行版）

按已确认顺序，`V0.4.0` 拆为 3 步：

1. 强化 `retrieval`
2. 把 `foreshadowing` 接入审查层
3. 补 `plan` 上层能力，并同步预埋 `V0.5.0` 需要的结构化摘要字段

---

## 3. 已完成项（截至当前）

## 3.1 Retrieval 强化（已完成）

已落地：

- 新增检索路由：`query_router`（`write_context` / `query` 策略位）
- `search_engine` 增强：
  - 稳定分片（句级优先）
  - 结果压缩（片段窗口）
  - 近重复去重（Jaccard）
  - 按章节限流（避免单章占满）
  - 来源权重（summary 与正文分权）
- 写作组包接入检索策略与路由结果

对应代码：

- `src/novelos/retrieval/query_router.py`
- `src/novelos/retrieval/search_engine.py`
- `src/novelos/workflow/context_package.py`

对应测试：

- `tests/test_retrieval.py`

## 3.2 Foreshadowing 审查接入（已完成）

已落地：

- 新增 `foreshadowing_checker`，检查三类风险：
  - 新伏笔是否清晰
  - 旧伏笔是否可能被当前章矛盾覆盖
  - 伏笔是否可能长期悬空
- 接入 `review.service_v2` 的统一审查返回
- 当前策略为告警型（warning/info），不进入 gatekeeper 拦截阈值
- `write_flow` 调整为“先抽取伏笔 -> 审查 -> 落盘复用”，避免重复抽取

对应代码：

- `src/novelos/review/foreshadowing_checker.py`
- `src/novelos/review/service_v2.py`
- `src/novelos/workflow/write_flow.py`

对应测试：

- `tests/test_foreshadowing_checker.py`
- `tests/test_review_smoke.py`

## 5. API 恢复后必须补做的验证

这些不影响当前结构关口，但影响版本最终质量验收：

1. `plan` 质量验证
- 卷级规划/节拍表/时间线的可用性与可读性
- 是否对后续写作质量产生稳定提升
- 若结果不达标，调整范围固定为：
  - 优先调整 `creation.outline_engine` 的 `plan_volume / plan_chapter_beats / plan_chapter_timeline` 提示词与输出约束
  - 必要时调整 `workflow.plan_flow` 的落盘结构字段和 `workflow.context_package` 的消费顺序
  - 不改 `workflow` 主调用方向与状态分层边界

2. `structured_summary` 新字段质量验证
- `high_point_markers` 是否能稳定定位强情节节点
- `reader_pull_marker` 的 `pull_type` 与 `evidence` 是否有判别价值
- 若结果不达标，调整范围固定为：
  - 优先调整 `creation.structured_summary_engine` 的提示词、解析与默认值策略
  - 必要时增加字段归一化与回填逻辑（保持字段名不变）
  - 不提前接入 `high_point / reader_pull` 拦截逻辑，仍保持“先数据、后 checker”

3. `foreshadowing_checker` 误报率评估
- 在真实章节中评估 warning 信号质量
- 决定是否在 `V0.5.0` 进入更强策略（如分级告警或局部拦截）
- 若结果不达标，调整范围固定为：
  - 优先调整 `review.foreshadowing_checker` 的规则阈值、关键词提取和冲突判定逻辑
  - 其次调整告警分级策略（`info/warning`）与输出文案
  - 暂不把该 checker 接入 gatekeeper 强拦截，避免在 `V0.4.0` 阶段误伤主链路

---

## 6. 进入 V0.5.0 的前置条件

满足以下条件即可进入 `V0.5.0` 开发：

1. API 恢复后，完成上述三类质量补测并形成结论。
2. 明确 `high_point` / `reader_pull` checker 的输入字段口径（已具备数据字段基础）。
3. gatekeeper 分级策略方案确认（拦截 / 告警 / 报告）。

---

## 7. 一句话总结

`V0.4.0` 的核心结构目标已完成：系统已从“最小检索+基础审查”升级到“可路由检索 + 伏笔审查接入 + 上层规划可消费 + V0.5字段就位”。
