# 基于 Codex 的长篇小说创作系统细化计划书 v3

## 0. 本次修订重点

这份 v3 不是推翻前面的计划，而是把已经确认的架构收敛正式落地。
本次重点修正 6 个问题：

1. 上下文组包不再放在创作层，而是提升为工作流桥接能力。
2. 增加统一 `foundation.llm_client`。
3. 检索层对外收敛为统一 `search_engine`。
4. `decision` 采用“规则信号 + 模型语义信号”的混合触发方式。
5. `workflow` 成为唯一流程控制中心。
6. 状态层、恢复切片和日志层的边界被明确分开。

## 1. 产品目标

我们要开发的是一个基于 Codex 的长篇小说协作系统。

它的目标不是一次性生成一章文，而是长期管理一部小说的创作过程，包括：

- 规划
- 写作
- 审查
- 状态维护
- 检索辅助
- 恢复
- 查询
- 决策交互

一句话概括：

它是“小说项目系统 + AI 写作团队”，不是“单次聊天写手”。

## 2. 我们准备实现的功能

### 2.1 核心功能

这些功能原则上全部保留：

1. 项目初始化
2. 题材约束与创意模板
3. 总纲、分卷、节拍表、时间线、章节规划
4. 章节写作流水线
5. 写前上下文准备
6. 多维审查
7. 审后修补与润色
8. 状态、摘要、索引回写
9. 实体、关系、场景、状态变化索引
10. RAG 检索辅助
11. 项目查询
12. 运行状态报告
13. 断点恢复
14. 询问与决策交互
15. 项目记忆学习
16. 只读 Dashboard

### 2.2 不按原样保留，但必须迁移的能力

这些不是删除，而是换宿主实现：

1. Claude Code 的 slash commands
   - 迁移为我们自己的命令入口
2. `SKILL.md` 的工作流表达方式
   - 迁移为我们自己的流程定义结构
3. Claude 风格子代理格式
   - 迁移为 Codex 兼容的角色分工和模块内调度
4. AskUserQuestion
   - 迁移为正式 `decision` 层
5. 插件市场分发
   - 不保留原形式，但不影响核心功能

## 3. 总体架构

系统建议拆成 8 层：

1. 交互入口层
2. 工作流编排层
3. 决策交互层
4. 创作执行层
5. 审查控制层
6. 记忆与检索层
7. 展示与运维层
8. 统一模型调用底座

### 3.1 交互入口层

负责：

- 接收用户命令
- 识别当前项目
- 启动具体流程

### 3.2 工作流编排层

负责：

- 定义 `init / plan / write / review / query / resume / learn / dashboard`
- 管理步骤顺序和执行状态
- 组装章节执行包
- 消费各模块返回的 signal
- 决定是否进入 `decision`

这里必须明确：

`workflow` 是唯一流程控制中心。

### 3.3 决策交互层

负责：

- 判断是否需要停下来问用户
- 构造清楚的问题和选项
- 记录用户裁决

触发方式分两类：

- 规则信号
  - 缺文件
  - 覆盖写入
  - 恢复分叉
  - 高风险操作确认
- 模型语义信号
  - 设定冲突
  - 信息不足
  - 路线分叉
  - 审查发现重大创作风险

### 3.4 创作执行层

负责：

- 初始化项目骨架
- 题材处理
- 大纲生成
- 正文起草
- 风格适配
- 审后修补和润色

它只消费工作流给出的执行包，不自己去做全局编排。

### 3.5 审查控制层

负责：

- 一致性检查
- 连贯性检查
- 人设检查
- 节奏检查
- 爽点检查
- 追读感检查
- 汇总审查报告

关键规则：

- 并行审查由 `review` 内部负责
- `workflow` 只看到一个统一 `review` 接口

### 3.6 记忆与检索层

负责：

- 项目长期状态
- 摘要
- 索引
- 检索
- 可恢复状态切片

本次明确修正：

- snapshots 不再单列成平级模块
- checkpoints、snapshots、review checkpoints 统一收口到状态层

### 3.7 展示与运维层

负责：

- 健康报告
- Dashboard
- 索引重建
- 状态诊断
- 向量重建

说明：

- `interaction -> presentation` 只允许纯展示入口
- 不允许借展示层推进业务流程

### 3.8 统一模型调用底座

这是本次新增的关键层。

负责：

- 提供统一模型调用入口
- 管理不同任务的模型配置
- 统一超时、重试、错误处理
- 统一记录日志、时延和成本
- 支持后续模型路由和替换

如果没有这一层，写作、审查和决策最后会变成“各调各的模型”。

## 4. 功能准备如何实现

### 4.1 初始化

实现思路：

- 工作流层先收集项目信息
- 创作层生成项目目录和模板
- 记忆层建立初始状态
- 基础层提供路径定位、配置和安全写入

最终实现：

- 用户可以创建一部新小说项目，并拿到完整骨架

### 4.2 规划

实现思路：

- 工作流层组织输入材料
- 创作层的大纲能力生成分卷、节拍表、时间线、章节大纲
- 记忆层保存结构化规划结果

最终实现：

- 用户可以把总纲展开成可持续写作的规划体系

### 4.3 写作

实现思路：

1. `workflow` 读取项目状态和章节要求
2. `workflow.context_assembler` 组装执行包
3. `retrieval` 提供相关召回
4. `creation.writer_engine` 生成草稿
5. `creation.style_engine` 做表达层处理
6. `review` 输出审查报告
7. 必要时进入 `decision`
8. `creation.polish_engine` 做修补与润色
9. `workflow -> memory` 正式回写

最终实现：

- 用户可以持续写章，并且每一章写完后系统状态同步更新

### 4.4 审查

实现思路：

- `workflow` 只调用一次 `review`
- `review` 内部并行调度多个 checker
- `review.report_builder` 汇总结果
- `review.gatekeeper` 给出是否允许继续的结论

最终实现：

- 系统可以对章节做多维质量检查，不依赖单一审稿口径

### 4.5 询问与决策

实现思路：

- 各业务模块只能返回 signal
- 所有 signal 统一回到 `workflow`
- `workflow` 判断是否进入 `decision`
- `decision` 负责构造问题、选项、风险说明并记录裁决

最终实现：

- 当系统拿不准时，会停下来和用户对齐，而不是擅自补完

### 4.6 状态、索引与恢复

实现思路：

- 项目长期状态归 `memory`
- 任务级执行状态归 `workflow.state_tracker`
- 可恢复切片统一归 `memory.state_store`
- 运行 trace 统一归 `foundation.logging`

最终实现：

- 系统可以安全恢复中断任务，也能保持整本书的长期一致

### 4.7 检索与 RAG

实现思路：

- `query_router` 判断意图
- `search_engine` 作为对外唯一检索入口
- 内部用策略切换关键词、向量或混合方式
- `rerank_engine` 做结果重排
- `context_recall` 专门服务写作上下文

最终实现：

- 新章节写作前可以精准调回相关前文

### 4.8 Dashboard 与状态报告

实现思路：

- `presentation.dashboard` 提供只读视图
- `presentation.status_report` 输出结构化健康报告
- `presentation.ops_tools` 提供重建和诊断工具

最终实现：

- 用户可以从系统外部视角看整本书的当前状态

## 5. 控制流规则

允许的主方向：

- `interaction -> workflow`
- `workflow -> creation`
- `workflow -> review`
- `workflow -> retrieval`
- `workflow -> decision`
- `workflow -> memory`
- `workflow -> presentation`

允许的例外：

- `interaction -> presentation`
  - 只限纯展示入口

禁止的方向：

- `creation -> decision`
- `review -> decision`
- `retrieval -> decision`
- `creation -> workflow`
- `review -> workflow`
- `memory -> workflow`
- `presentation -> workflow`

关键原则：

- 模块可以内部调度，但不能越级控制全局流程
- 并行审查是 `review` 内部实现，不暴露给 `workflow`

## 6. 状态作用域规则

### 6.1 项目级长期状态

作用域：

- `project_id`

负责保存整本书的长期真相。

### 6.2 任务级短期状态

作用域：

- `project_id + task_id`

负责保存单次流程执行状态。

### 6.3 可恢复状态切片

负责保存：

- checkpoints
- snapshots
- review checkpoints
- chapter execution snapshots

说明：

- 它们是业务可恢复数据
- 不等于日志

### 6.4 运行日志

负责保存：

- 调用链
- 错误
- 性能
- 调试轨迹

说明：

- 日志用于观测和排障
- 不是业务真相

## 7. 暂时不保留原样的部分

只有两类内容不按原样保留：

1. Claude Code 宿主形式
   - 包括 slash commands、原生 `SKILL.md` 触发方式、插件分发形式
2. 早期过细的检索引擎拆分
   - 不影响功能，只是收敛实现结构

重点说明：

这些都不是功能删除，而是迁移实现。
原项目的能力体系仍然保留。

## 8. 当前阶段的硬约束

在正式开工前，建议把这些视为不可轻易改动的底层约束：

1. 所有模型调用统一走 `foundation.llm_client`
2. 所有章节写作先由 `workflow` 组装执行包
3. 检索层对外只暴露一个 `search_engine`
4. 所有高影响分叉只由 `workflow` 决定是否进入 `decision`
5. `review` 对外必须保持黑盒接口
6. `state_tracker` 的作用域固定为 `project_id + task_id`
7. 可恢复切片和运行日志必须分层保存

## 9. 结论

这一版计划的重点，不是增加新功能，而是把原项目的完整能力迁移到 Codex 体系下，并把几个最容易塌的边界提前封住。

只要控制流、状态分层、上下文组包、统一模型调用这四件事先定死，后面的实现就会稳很多。
