# 模块调用方向与状态作用域规范

## 0. 文档目的

这份文档不讨论功能细节，只做三件事：

1. 规定模块调用方向
2. 规定哪些调用方向是例外、哪些是禁止的
3. 规定状态分层与状态作用域

它的作用是给后续实现“封顶”，防止系统从分层结构滑向网状耦合。

---

## 1. 核心原则

### 1.1 `workflow` 是唯一流程控制中心

只有 `workflow` 可以决定：
- 下一步执行哪个模块
- 当前流程是否暂停
- 是否进入询问
- 是否继续、回滚、恢复、结束

其他模块都不能直接改变流程走向。

### 1.2 模块可以有内部调度，但不能越级控制全局流程

例如：
- `review` 可以在内部并行调度多个 checker
- `creation` 可以在内部组织自己的生成与修订子步骤

但这些都属于模块内部实现，不等于它们拥有全局流程控制权。

### 1.3 所有高影响分叉都必须回到 `workflow`

不管信号来自：
- `creation`
- `review`
- `retrieval`

最终都只能返回给 `workflow`，由 `workflow` 决定是否进入 `decision`。

---

## 2. 一级模块列表

系统当前定义的一级模块：

1. `foundation`
2. `interaction`
3. `workflow`
4. `decision`
5. `creation`
6. `review`
7. `memory`
8. `retrieval`
9. `presentation`

---

## 3. 允许的主调用方向

## 3.1 标准主链路

允许的主调用方向如下：

- `interaction -> workflow`
- `workflow -> creation`
- `workflow -> review`
- `workflow -> retrieval`
- `workflow -> decision`
- `workflow -> memory`
- `workflow -> presentation`

这条链路适用于绝大多数业务流程：
- 初始化
- 规划
- 写作
- 审查
- 查询
- 恢复
- 启动 Dashboard
- 生成健康报告

## 3.2 基础能力调用

允许所有业务模块调用 `foundation` 提供的基础能力。

例如：
- `workflow -> foundation`
- `creation -> foundation`
- `review -> foundation`
- `decision -> foundation`
- `memory -> foundation`
- `retrieval -> foundation`
- `presentation -> foundation`

但这里的调用只能是“基础设施调用”，例如：
- 项目定位
- 配置读取
- 安全读写
- 日志
- 模型调用

不代表 `foundation` 会反向驱动业务流程。

---

## 4. 允许的例外方向

## 4.1 `interaction -> presentation`

这是唯一需要显式写出来的例外。

允许：
- `interaction -> presentation`

但仅限：
- 打开只读 Dashboard
- 打开展示界面
- 展示现成报告文件

不允许：
- 在这个调用里做业务判断
- 在这个调用里推进流程
- 在这个调用里更新项目状态

也就是说：

### 可以
- “打开一个现成页面”

### 不可以
- “前台直接让展示层决定该读什么、写什么、跳到哪一步”

通俗比喻：
- 前台可以帮你打开监控屏幕，但不能让监控屏幕反过来指挥生产线。

---

## 5. 禁止的调用方向

下面这些方向明确禁止。

## 5.1 与 `workflow` 相关的禁止项

禁止：
- `creation -> workflow`
- `review -> workflow`
- `decision -> workflow`
- `memory -> workflow`
- `retrieval -> workflow`
- `presentation -> workflow`

解释：
- 这些模块不能反向控制工作流
- 它们只能返回结果或信号

## 5.2 与 `decision` 相关的禁止项

禁止：
- `creation -> decision`
- `review -> decision`
- `retrieval -> decision`
- `memory -> decision`

解释：
- 这些模块不能直接去“问用户”
- 它们只能返回 `decision signal` 给 `workflow`
- 是否进入 `decision`，必须由 `workflow` 决定

这是本系统的一条硬规则。

## 5.3 与 `memory` 相关的禁止项

禁止：
- `interaction -> memory`
- `presentation -> memory`（写入）
- `review -> memory`（直接回写最终状态）
- `creation -> memory`（直接推进流程状态）

解释：
- `memory` 只接受 `workflow` 组织后的写入
- 防止多个模块绕过流程直接改项目真相

## 5.4 与 `presentation` 相关的禁止项

禁止：
- `presentation -> creation`
- `presentation -> review`
- `presentation -> decision`
- `presentation -> memory`（业务写入）

解释：
- 展示层不能成为隐形业务入口

---

## 6. 模块允许返回的内容类型

为了避免“不能直接控制流程”变成一句空话，需要规定模块可以返回什么。

除 `workflow` 外，其他模块对外只能返回以下两类内容：

### 6.1 业务结果

例如：
- 章节草稿
- 审查报告
- 检索结果
- 状态读取结果
- 可视化内容

### 6.2 标准化信号

例如：
- `decision_required`
- `missing_required_input`
- `conflict_detected`
- `recovery_risk_high`
- `write_blocked`

信号的作用：
- 提醒 `workflow` 当前出现了需要处理的情况

信号的限制：
- 信号不是命令
- 信号不能自己改变流程

也就是说：

- `review` 可以返回：`decision_required`
- 但 `review` 不能自己调 `decision`

---

## 7. `review` 的内部并行调度规则

这是本规范里必须单独写清的一条。

## 7.1 原则

`workflow` 不直接调单个 checker。

正确结构是：

- `workflow -> review`
- `review` 内部并行调度：
  - consistency checker
  - continuity checker
  - character checker
  - pacing checker
  - high-point checker
  - reader-pull checker
- `review` 再统一汇总为一个报告返回 `workflow`

## 7.2 这样设计的原因

如果让 `workflow` 直接调所有 checker，会产生三个问题：

1. `workflow` 过度了解 `review` 的内部结构
2. checker 组合一变，`workflow` 接口就跟着变
3. review 模块会退化成一个很薄的拼接层

因此必须明确：

### `review` 是一个黑盒模块

对外只暴露：
- 审查请求接口
- 审查结果接口
- 必要时的标准化 signal

对内才允许并行调度多个 checker。

---

## 8. `decision signal` 的消费规则

这是上一轮讨论里暴露出的关键问题，这里正式定下来。

## 8.1 信号来源

`decision signal` 可以来自：

- `creation`
- `review`
- `retrieval`
- `workflow` 自己的规则检查

## 8.2 唯一消费者

所有 `decision signal` 的唯一消费者都是：

- `workflow`

## 8.3 标准处理流程

处理顺序必须是：

1. 某业务模块返回业务结果或 signal
2. `workflow` 接收该结果
3. `workflow` 判断是否需要进入 `decision`
4. 如需要，则 `workflow -> decision`
5. `decision` 组织问题、选项、风险说明并拿回用户裁决
6. 裁决结果返回 `workflow`
7. `workflow` 决定后续走向

结论：

- `decision` 不直接打断流程
- `decision` 不直接推进流程
- `decision` 只是“裁决交互模块”

---

## 9. 状态分层规则

系统状态必须分层，不允许所有状态混成一团。

建议分成 4 层：

1. 项目级长期状态
2. 任务级短期状态
3. 可恢复状态切片
4. 运行观测日志

---

## 10. 状态作用域规则

## 10.1 项目级长期状态

作用域：
- `project_id`

存放内容：
- 当前写到哪
- 主角状态
- 世界状态
- 伏笔状态
- 关系状态
- 章节元信息
- 项目记忆

归属模块：
- `memory`

特点：
- 是整本书的“长期真相”

## 10.2 任务级短期状态

作用域：
- `project_id + task_id`

存放内容：
- 当前执行的是哪个命令
- 当前执行到哪一步
- 哪些步骤已完成
- 哪些步骤失败
- 当前任务产物信息

归属模块：
- `workflow.state_tracker`

特点：
- 是一次流程执行的“短期状态”
- 不等于项目长期状态

这是本规范里明确的一条：

### `state_tracker` 的主作用域是任务，不是项目

但任务一定挂在项目下，所以实际粒度是：

`project_id + task_id`

## 10.3 可恢复状态切片

作用域：
- `project_id`
- 必要时关联 `task_id`

存放内容：
- workflow checkpoints
- resume snapshots
- review checkpoints
- chapter execution snapshots

归属模块：
- `memory.state_store`

特点：
- 这些数据是结构化的
- 会被恢复流程和诊断流程再次消费

## 10.4 运行观测日志

作用域：
- 可按 project / task / process 多维度记录

存放内容：
- 调用链日志
- 错误日志
- 性能日志
- 调试轨迹

归属模块：
- `foundation.logging`

特点：
- 只用于观测和排障
- 不作为业务恢复的真实来源

这条是必须强调的：

### 运行 trace 不属于状态层

它属于日志层。

---

## 11. 状态层与日志层的边界

这部分容易混，所以单独写清。

### 属于 `memory.state_store` 的

- checkpoint
- snapshot
- review checkpoint
- 可恢复执行切片

### 属于 `foundation.logging` 的

- workflow trace
- 调用明细
- 错误堆栈
- 性能观测
- 调试输出

通俗比喻：

- `state_store` 像存档点
- `logging` 像监控录像

存档点用于恢复游戏进度。  
监控录像用于事后排查发生了什么。

它们不能混。

---

## 12. 最终硬规则

把前面的内容压缩成最重要的 8 条硬规则：

1. `workflow` 是唯一流程控制中心
2. 业务模块只能返回结果或 signal，不能直接改流程走向
3. 任何 `decision signal` 只能由 `workflow` 消费
4. `creation`、`review`、`retrieval` 都不能直接调用 `decision`
5. `review` 可以内部并行调度 checker，但对外必须保持黑盒接口
6. `interaction -> presentation` 仅允许纯展示入口，不能带业务判断
7. `state_tracker` 的作用域是 `project_id + task_id`
8. traces 属于日志层，不属于状态层

---

## 13. 一句话总结

这套规范真正要防的不是“写不出来”，而是“模块之间越写越乱”。

只要调用方向和状态作用域先封口，后面实现再复杂，也不容易长成一张网。
