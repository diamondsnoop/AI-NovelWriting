# 基于 Codex 的长篇小说创作系统细化计划书

## 0. 计划书目的

这份计划书基于 `webnovel-writer` 项目的 `docs/`、`skills/`、`scripts/`、`dashboard/` 等内容整理，目标不是复述原项目，而是把它的完整功能、用户使用流程和系统支撑方式迁移成一份适合我们自己产品的开发计划。

本计划书遵循三条原则：

1. 功能尽量保留  
原项目真正有价值的能力，原则上都要保留。

2. Claude Code 独有能力不硬抄，但不直接丢掉  
要做“功能迁移”，不是“功能删减”。

3. 先定义产品骨架，再决定实现节奏  
当前不区分 MVP 与后续阶段，先把完整产品轮廓定清楚。

---

## 1. 对原项目的完整理解

### 1.1 原项目本质

`webnovel-writer` 不是一个“写小说提示词集合”，也不是一个“单次生成器”。

它本质上是一个：

- 面向长篇网文创作的流程系统
- 面向长期连载的记忆系统
- 面向创作质量的审查系统
- 面向中断与维护的运行系统

通俗地说，它像一个“小说创作操作系统”。

### 1.2 原项目中，用户能做什么

从 `docs/commands.md`、`README.md` 和各个 `skills/` 可确认，原项目用户可以做这些事：

1. 初始化一个新小说项目  
命令：`/webnovel-init`

2. 为某一卷做规划  
命令：`/webnovel-plan 1`、`/webnovel-plan 2-3`

3. 写某一章  
命令：`/webnovel-write 1`、`/webnovel-write 45`

4. 用不同强度模式写作  
- 标准模式
- `--fast`
- `--minimal`

5. 审查一个章节范围  
命令：`/webnovel-review 1-5`

6. 查询项目里的信息  
例如：
- 查角色
- 查伏笔
- 查节奏
- 查金手指状态
- 查 Strand 分布

7. 恢复被中断的任务  
命令：`/webnovel-resume`

8. 启动只读 Dashboard  
命令：`/webnovel-dashboard`

9. 把对话中的有效写作模式沉淀进项目记忆  
命令：`/webnovel-learn`

10. 做运维和诊断  
例如：
- 预检查
- 状态报告
- 索引重建
- 向量重建
- 测试

### 1.3 原项目完整用户流程

用户主流程大致是：

1. 安装插件和依赖
2. 初始化小说项目
3. 填写或完善设定、大纲、题材约束
4. 规划分卷和章节
5. 写章节
6. 对章节做审查
7. 在写作中随时查询设定、伏笔、状态
8. 如流程中断则恢复
9. 用 Dashboard 查看全局情况
10. 把好的写法沉淀进项目记忆
11. 持续迭代直到长篇完成

原项目最重要的特点是：  
它不是“写一章就结束”，而是“每写完一章，系统都更新整本书的状态，为下一章做准备”。

## 2. 我们的产品目标

我们要开发的是一个：

**基于 Codex 的长篇小说创作系统**

目标不是复刻 Claude Code 外壳，而是保留 `webnovel-writer` 的完整创作能力和工作流价值。

一句话定义：

> 让 AI 和用户协同管理一部长篇小说，从立项、设定、规划、写作、审查、查询、恢复到可视化，形成可长期运行的闭环。

## 3. 我们要实现的功能

下面按“用户可感知的功能”来列，不按技术模块列。

### 3.1 项目初始化

用户能力：
- 创建一部新小说项目
- 输入书名、题材、篇幅目标、主角、金手指、世界观等基础信息
- 自动生成统一目录、设定模板、总纲模板、状态文件

保留原因：
- 这是所有后续流程的入口
- 原项目非常强调“先搭骨架，再开始写”，这个逻辑必须保留

### 3.2 题材与创意约束管理

用户能力：
- 选择单题材或复合题材
- 生成题材约束包
- 引入反套路、卖点、市场定位、读者方向等信息

保留原因：
- 原项目不仅写小说，还试图帮助用户明确“这本书要怎么卖、怎么立”
- 这是规划质量的重要来源

### 3.3 总纲、分卷、章节规划

用户能力：
- 从总纲扩展为卷级规划
- 生成节拍表、时间线、卷摘要、章节大纲
- 为具体章节写作做准备

保留原因：
- 这是长篇创作稳定性的关键
- 如果没有这一层，后续写作会迅速跑偏

### 3.4 章节写作流水线

用户能力：
- 指定章节编号开始写作
- 选择标准、快速、最简模式
- 自动走完“准备上下文 -> 起草 -> 审查 -> 润色 -> 回写”

保留原因：
- 这是原项目最核心的主链路
- 必须保留为完整流水线，而不是退化成“直接生成正文”

### 3.5 写前上下文准备

用户能力：
- 在写第 N 章之前，系统自动整理：
  - 本章大纲
  - 上几章摘要
  - 当前主角状态
  - 关键伏笔
  - 节奏要求
  - 题材约束

保留原因：
- 原项目防“失忆”和防“胡编”的关键在这里

### 3.6 多维质量审查

用户能力：
- 对单章或章节范围做质量检查
- 获取结构化审查报告
- 查看综合评分、严重问题、改进建议

检查维度应保留：
- 设定一致性
- 剧情连贯性
- 人设/OOC
- 节奏控制
- 爽点密度
- 追读感

保留原因：
- 原项目的价值不只是能写，更是能发现“写崩”的地方

### 3.7 润色与修订

用户能力：
- 根据审查结果修复严重问题
- 优化表达、排版、可读性
- 在不改核心事实的前提下调整文风

保留原因：
- 原项目明确区分“生成”和“修复”，这有助于保持流程清晰

### 3.8 状态、记忆与索引管理

用户能力：
- 系统持续记录：
  - 当前写到哪
  - 总字数
  - 当前卷
  - 人物状态
  - 世界状态
  - 关系变化
  - 伏笔状态
  - 章节元信息

保留原因：
- 长篇写作不是一次会话，必须有外部状态系统

### 3.9 实体、关系、场景与章节索引

用户能力：
- 快速查人物、地点、势力、物品、关系、场景切片
- 支撑高效检索和 Dashboard 展示

保留原因：
- 原项目把大量信息从 `state.json` 迁到 `index.db`，这是合理设计

### 3.10 RAG 检索辅助

用户能力：
- 写作和查询时检索前文相关片段
- 根据查询类型走不同检索策略
- 在 embedding 不可用时自动回退

保留原因：
- 这是原项目处理长篇上下文不足的重要手段

### 3.11 项目查询

用户能力：
- 查角色
- 查境界/能力/力量体系
- 查势力和地点
- 查伏笔紧急度
- 查 Strand 节奏情况
- 查金手指状态

保留原因：
- 用户需要“盘书”能力，而不是只能不断生成新内容

### 3.12 运行状态报告

用户能力：
- 生成健康报告
- 看角色掉线情况
- 看伏笔超时情况
- 看爽点与节奏分布
- 看关系图谱

保留原因：
- 对长篇项目来说，这是运营和质量管理的重要视角

### 3.13 断点恢复

用户能力：
- 检测中断任务
- 查看中断位置和已完成步骤
- 选择恢复方式
- 安全清理半成品或回滚

保留原因：
- 原项目对“恢复”非常重视，这个能力必须保留

### 3.14 询问与决策交互

这是我们额外强调、但其实也符合原项目精神的功能。

用户能力：
- 当系统遇到不确定问题时，由系统主动询问用户
- 用户决定方向后，系统再继续

必须纳入的询问场景：
- 信息缺失
- 设定冲突
- 方向分叉
- 高风险修改
- 恢复策略选择
- 审查发现重大问题时的处理方式

保留原因：
- 这是避免 AI 擅自决定创作方向的关键
- 原项目中 `AskUserQuestion` 已有雏形，我们要把它升级成正式产品能力

### 3.15 项目记忆学习

用户能力：
- 把当前对话或某段创作中总结出的“有效写法”写入项目记忆
- 例如：
  - 钩子模式
  - 节奏模式
  - 对话风格
  - 微兑现写法

保留原因：
- 这是原项目的一个小但很有价值的功能
- 它让系统不仅记“故事事实”，还记“写作经验”

### 3.16 只读 Dashboard

用户能力：
- 以图形方式查看项目状态
- 看人物关系、章节进度、设定词典、阅读力数据

保留原因：
- 原项目已经把这部分做成完整功能，不应直接放弃

## 4. 这些功能准备如何实现

这一部分只讲实现思路与模块分工，不出现代码。

## 4.1 总体架构

我们建议把系统拆成 7 层：

1. 交互入口层
2. 工作流编排层
3. 决策交互层
4. 创作执行层
5. 审查控制层
6. 记忆与检索层
7. 展示与运维层

### 4.1.1 交互入口层

负责：
- 接收用户命令
- 识别当前项目
- 启动具体流程
- 对外提供统一入口

迁移说明：
- 原项目依赖 Claude Code 的 slash commands
- 我们不保留原样，但保留“统一命令入口”这个能力
- 迁移为我们自己的 CLI / 会话命令系统

### 4.1.2 工作流编排层

负责：
- 定义 init / plan / write / review / query / resume / learn / dashboard 的流程
- 定义每一步的前后依赖
- 定义哪些模式允许跳步，哪些不允许

迁移说明：
- 原项目用 `SKILL.md` 表达流程
- 我们不照搬文件格式，但保留“每个命令都是一套正式流程”的思想

### 4.1.3 决策交互层

负责：
- 判断什么时候系统必须停下来问用户
- 统一管理询问类型、选项、风险提示
- 记录用户的裁决结果

这层是我们明确加强的部分。

它相当于系统的“红灯机制”：
- 遇到小问题，AI 自行处理
- 遇到大问题，必须红灯停车，等用户决定

### 4.1.4 创作执行层

负责：
- 初始化项目骨架
- 规划总纲、分卷、章节
- 写前准备
- 正文起草
- 风格适配
- 润色修订

这层不是单一模型调用，而是多阶段任务。

### 4.1.5 审查控制层

负责：
- 多维检查
- 结构化评分
- 严重问题拦截
- 审查结果汇总
- 修订建议输出

保留原项目的检查维度，但实现上改为 Codex 兼容的内部角色或任务分工。

### 4.1.6 记忆与检索层

负责：
- 轻量运行状态
- 实体与关系索引
- 章节摘要
- 向量检索
- 规则检索
- 场景切片

建议保持“三层数据”设计：
- `state.json`：轻量运行状态
- `index.db`：结构化索引
- `vectors.db`：语义检索

### 4.1.7 展示与运维层

负责：
- 健康报告
- Dashboard
- 索引重建
- 状态诊断
- 测试与恢复辅助

## 4.2 逐功能实现思路

### 4.2.1 初始化如何实现

实现方式：
- 设计一个初始化工作流
- 先收集基础信息
- 再生成目录、模板和基础状态
- 将题材模板、世界观模板、总纲模板按规则注入项目

需要的内部模块：
- 项目定位模块
- 模板渲染模块
- 初始状态生成模块
- 用户提问模块

### 4.2.2 规划如何实现

实现方式：
- 读取总纲和设定
- 在卷级别先做节拍表和时间线
- 再分批生成章节大纲
- 把规划结果回写到项目里

需要的内部模块：
- 大纲解析模块
- 分卷规划模块
- 节拍生成模块
- 时间线生成模块
- 章节规划模块

### 4.2.3 写作如何实现

实现方式：
- 先构建“写作任务包”
- 再进行正文生成
- 再进行可选风格适配
- 再进行审查
- 再修复和润色
- 最后回写状态与索引

关键点：
- 写作功能必须始终是“流水线”
- 不能退化成单轮直接出正文

### 4.2.4 审查如何实现

实现方式：
- 为每一类检查定义独立审查职责
- 可以由多个内部角色并行处理
- 最后统一汇总成结构化报告

保留点：
- 设定一致性
- 连贯性
- OOC
- 节奏
- 爽点
- 追读感

迁移说明：
- 原项目的 checker agent 机制不直接保留文件形态
- 但“多检查员并行质检”这个能力必须保留

### 4.2.5 状态与索引如何实现

实现方式：
- 轻量运行状态放到 JSON
- 高频查询和大数据量内容放到 SQLite
- 章节写完后增量更新
- 对关键文件加锁与校验

这样做的原因：
- JSON 适合存当前状态
- SQLite 适合存大量实体和关系
- 语义检索需要独立向量存储

### 4.2.6 RAG 如何实现

实现方式：
- 对用户查询或写作上下文做意图判断
- 根据意图决定用哪种检索策略
- 有语义检索时走向量 + rerank
- 没有时回退到关键词检索

保留点：
- QueryRouter
- 多路检索
- 回退机制
- Top-K 结果供写作和查询使用

### 4.2.7 查询如何实现

实现方式：
- 给查询功能单独定义流程
- 先识别用户在查什么
- 再读取状态、设定、索引与检索结果
- 最后结构化输出

查询类型至少保留：
- 角色
- 势力
- 世界设定
- 金手指
- 伏笔
- Strand
- 紧急度/健康度

### 4.2.8 恢复如何实现

实现方式：
- 为每个任务记录步骤级状态
- 任务中断后，检测停在何处
- 按步骤类型给出恢复建议
- 必须让用户确认恢复策略

必须保留的原则：
- 不盲续写
- 不跳过检测
- 不自动替用户选择高风险恢复方式

### 4.2.9 询问机制如何实现

实现方式：
- 在所有流程里植入统一的“决策点”
- 每个决策点定义：
  - 触发条件
  - 询问内容
  - 可选项
  - 默认建议
  - 执行后果

询问类型建议分为：
- 补信息型
- 冲突裁决型
- 路线分叉型
- 高风险确认型

这会成为整个产品的重要骨架，不是附加功能。

### 4.2.10 Learn 功能如何实现

实现方式：
- 接收用户输入的“这次写法哪里好”
- 自动归类为某种模式
- 追加写入项目记忆文件
- 后续在写作上下文中可选择引用

这个功能小，但很适合做成长期学习能力。

### 4.2.11 Dashboard 如何实现

实现方式：
- 维持只读原则
- 从项目数据层读取信息
- 用本地 Web 界面展示
- 支持自动刷新

迁移说明：
- 原项目是 Claude 插件里的 Dashboard
- 我们应迁移成独立的本地只读面板，而不是依赖 Claude 宿主

## 5. Claude Code 独特能力的迁移方案

这一部分是重点。不是放弃，而是迁移。

### 5.1 Slash Commands 的迁移

原能力：
- `/webnovel-init`
- `/webnovel-plan`
- `/webnovel-write`
- `/webnovel-review`
- `/webnovel-query`
- `/webnovel-resume`
- `/webnovel-dashboard`
- `/webnovel-learn`

迁移方案：
- 改为我们自己的命令入口
- 保留命令语义，不保留 Claude 的命令宿主形式

例如：
- `novel init`
- `novel plan`
- `novel write`
- `novel review`
- `novel query`
- `novel resume`
- `novel dashboard`
- `novel learn`

结论：
- 功能保留
- 实现形式迁移

### 5.2 Skills 的迁移

原能力：
- `SKILL.md` 定义流程、工具权限、步骤约束

迁移方案：
- 把 Skill 的价值拆成两部分保留：
  1. 流程定义
  2. 资源加载规则

- 不必继续沿用 Claude Code 的文件约定
- 但必须保留“每个功能是一个正式流程”的思想

### 5.3 Agents 的迁移

原能力：
- `context-agent`
- `data-agent`
- 多个 checker agent

迁移方案：
- 改为 Codex 系统内部的角色分工或任务分工
- 保留职责边界，不保留 Claude 的 agent markdown 宿主格式

### 5.4 Task 调子代理的迁移

原能力：
- 主流程通过 Task 工具调起子代理并汇总结果

迁移方案：
- 用我们自己的工作流编排器或内部任务执行器替代
- 重点保留：
  - 步骤可分解
  - 子任务可并行
  - 结果可汇总

### 5.5 AskUserQuestion 的迁移

原能力：
- 在初始化、审查、恢复中向用户提问

迁移方案：
- 升级为正式“决策交互层”
- 不仅保留，还要增强

### 5.6 Workspace/Project Pointer 的迁移

原能力：
- `.claude/.webnovel-current-project`
- `CLAUDE_PROJECT_DIR`
- `CLAUDE_PLUGIN_ROOT`

迁移方案：
- 保留“工作区”和“真实小说项目根目录”分离的思想
- 用我们自己的项目定位机制代替
- 保留“当前激活项目指针”能力

### 5.7 Plugin Marketplace 的迁移

原能力：
- 通过 Claude 插件市场安装

迁移方案：
- 不保留原分发方式
- 这是唯一明确不保留的“宿主级能力”

原因：
- 它和小说系统本身能力无关
- 只影响安装方式，不影响创作功能

这是“实现形式删除”，不是“功能删除”。

## 6. 哪些功能暂时不建议删除

下面这些功能虽然实现成本不同，但按当前理解，都不建议直接删：

1. 初始化
2. 规划
3. 写作流水线
4. 多维审查
5. 状态管理
6. 实体/关系/章节索引
7. RAG 检索

9. 恢复
10. 询问机制
11. Learn 项目记忆

## 7. 如果必须缩减，优先缩减什么

虽然我们当前不讨论 MVP，但为了防止后面失控，还是要明确“能保留”和“必须缩减时先缩什么”。

### 可以后移，但不建议删除的

1. Dashboard 的复杂图形展示  
核心数据先保留，复杂前端后移。

2. 健康报告中的高级图谱与热力图  
基础报告先做，图形表现后做。

3. Learn 功能中的高级模式归纳  
先做简单追加，再做复杂学习。

4. 复杂的阅读力债务系统  
基础追读感检查先做，债务利息模型后做。

### 不应削弱的

1. 写作流水线
2. 状态回写
3. 多维审查
4. 询问机制
5. 查询能力
6. 恢复能力

这些属于产品底座。

## 8. 我们的产品骨架结论

基于当前对原项目的重新理解，我们的产品应定义为：

### 8.1 产品本体

一个基于 Codex 的长篇小说创作系统。

### 8.2 核心目标

不是替用户一次性写文，而是帮助用户长期管理和推进一部小说。

### 8.3 核心闭环

初始化 -> 规划 -> 写作 -> 审查 -> 回写 -> 查询/恢复 -> 下一轮写作

### 8.4 核心差异点

相对普通写作工具，我们的核心差异点应是：

1. 有完整工作流
2. 有长期记忆
3. 有结构化审查
4. 有主动询问
5. 有断点恢复
6. 有项目级查询和可视化

### 8.5 对原项目的迁移策略

我们不复制 Claude Code 宿主形式，但尽量完整保留原项目的创作能力与运行逻辑。

也就是说：

- 保留“功能体系”
- 保留“流程思想”
- 保留“状态设计”
- 保留“检索与审查”
- 保留“询问与恢复”
- 迁移“宿主能力”
- 放弃“Claude 插件分发形式”
